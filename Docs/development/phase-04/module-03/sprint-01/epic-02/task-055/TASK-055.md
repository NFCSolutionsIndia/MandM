## 1. Objective

Build the endpoint that mints short-lived signed URLs for media variants, gated by `lib/authz` and rate-limited per user.

---

## 2. Context

Blueprint §12.5 requires that access is "always via short-TTL signed URLs, minted only after an authorisation check", with five minutes for viewing and sixty for downloads, plus "hotlink protection and per-user rate limiting on signed-URL minting to prevent a leaked link from being used as a CDN".

---

## 3. Problem Statement

This endpoint is the single door to every byte of user media. If it mints without checking authorization, every other protection in the system is irrelevant. The short TTL is also what makes revocation meaningful: blueprint §11.3 notes that because signed URLs live five minutes, "real-world exposure after revocation is bounded to minutes rather than forever".

---

## 4. Expected Outcome

An endpoint returning signed URLs for requested variants after an authz check, with distinct TTLs for view and download, per-user rate limits, and download rights honoured per the permission matrix.

---

## 5. Requirements

### Functional Requirements

- Request a variant (thumb, preview, original, HLS playlist) for an asset; receive a signed URL.
- Authz check via `lib/authz` before minting, using the asset's memory and vault.
- View TTL five minutes; download TTL sixty minutes.
- Download requires the download-right cell from the permission matrix.
- Rate limit 300 mints per minute per user (§20.6).
- Batch minting for a grid page, so a screen of 40 thumbnails is one request rather than 40.

### Technical Requirements

- Signed URLs generated by the storage client; never constructed by hand.
- The response carries the expiry so the client can pre-emptively refresh rather than waiting for a 403.
- Batch requests are authz-checked per asset, not once for the batch — a batch must not become a way to smuggle one unauthorised asset in with thirty authorised ones.
- Hotlink protection configured at the CDN, and the configuration recorded in §20 since it is not code.

---

## 6. Implementation Instructions

1. Create `/api/media/[id]/url` for a single asset and `/api/media/urls` for a batch.
2. Resolve the asset's memory and vault, then call `authorize()` with the view or download action. **Check every asset in a batch individually.**
3. Mint with the appropriate TTL. Return the expiry timestamp alongside the URL.
4. Honour the download-right matrix cell: a viewer without download rights gets a view URL only, and asking for a download returns a specific denial.
5. Add the rate limit from §20.6, and make the 429 response carry `Retry-After`.
6. Configure CDN caching as `private, max-age=300` for signed variants (§12.5), and record the hotlink-protection configuration in §20.
7. Write the cross-user denial test and the batch-smuggling test — the latter is the non-obvious one.

## 10. API Contract

### Endpoint

```text
POST /api/media/urls
```

### Request

```json
{
  "assets": [
    { "id": "uuid", "variant": "thumb" },
    { "id": "uuid", "variant": "preview" }
  ],
  "purpose": "view"
}
```

### Response

```json
{
  "ok": true,
  "data": {
    "urls": [
      { "id": "uuid", "variant": "thumb", "url": "https://…", "expiresAt": "2026-08-26T10:05:00Z" }
    ]
  }
}
```

### Validation

- Each asset authorized individually
- Variant exists and is ready
- Purpose is view or download
- Download requires the download-right cell
- Batch size bounded

### Error Responses

| Status | Code | When |
|---|---|---|
| 403 | `AUTHZ_DENIED` | No grant on the asset's vault |
| 403 | `MEDIA_DOWNLOAD_NOT_PERMITTED` | Download right absent for this role or share |
| 404 | `MEDIA_VARIANT_NOT_READY` | Still transcoding, or the variant does not exist for this source |
| 429 | `RATE_LIMIT_MEDIA_URL` | More than 300 mints per minute |

## 12. Business Rules

- **Authz before minting, every time, per asset.**
- View TTL five minutes; download sixty.
- Download rights come from the permission matrix, not from a request parameter.
- Batch requests are checked per asset.
- No bucket object is ever publicly readable.

---

## 13. Edge Cases

- **A batch containing one unauthorised asset among thirty authorised ones — the unauthorised one must be denied individually, and the response must not leak whether it exists.** This is the subtle failure this endpoint invites.
- A variant still transcoding — return a specific not-ready code so the UI can show a processing state rather than a broken image.
- A variant that does not exist for this source (a 2048 width for a 900px photo) — return the largest available and say which, rather than 404-ing.
- A share-link holder requesting a download when the share disallows it — denied by the matrix.
- A capsule recipient requesting media before delivery — denied; the pre-delivery invisibility rule from §11.4 is enforced here, not just in the UI.
- A user hitting the rate limit while scrolling a large grid — batching should prevent it; if it happens, the 429 must carry `Retry-After` and the UI must back off rather than hammering.
- A URL requested and then used 6 minutes later — 403; the client refreshes using the returned expiry.

---

## 14. Error Handling

- Every denial is specific enough for the UI to act on, without revealing whether an asset exists in another vault.

---

## 15. Security Considerations

- Per-asset authz in batches.
- Short TTLs, which is also what bounds post-revocation exposure (§11.3).
- Rate limits with `Retry-After`.
- Hotlink protection at the CDN, recorded in §20.
- Pre-delivery capsule media must be unreachable through this endpoint, not merely hidden in the UI.

---

## 16. Testing Requirements

### API Tests

- Cross-user request denied.
- **Batch with one unauthorised asset denies that asset without leaking existence.**
- Not-ready variant returns the specific code.
- Missing width falls back to the largest available with the variant named.
- Download denied without the download right.
- Rate limit returns 429 with `Retry-After`.

### Security Tests

- Pre-delivery capsule media is unreachable via this endpoint (stub until PHASE-05, then re-run).
