## 1. Epic Objective

Build the chunker, the durable outbox, and the queue UI.

---

## 2. Business Value

This epic is the one that delivers the promise "nothing is ever lost". Everything else in the phase supports it.

---

## 3. User Stories

> **As a** user with one bar of signal
> **I want** my upload to keep trying by itself
> **So that** I do not have to babysit a progress bar

> **As a** user
> **I want** to see exactly what is still uploading
> **So that** I know whether it is safe to close the app

---

## 4. Functional Requirements

- Chunk, upload three parts in parallel, resume from last confirmed
- Outbox with per-item state and backoff
- Queue tray with pause, resume, cancel, retry
- Connection-aware deferral

---

## 5. Technical Requirements

- Room / GRDB outbox with an explicit state machine
- Idempotency keys on every mutation
- `StorageManager.persist()` with a denial warning
- `Save-Data` and `effectiveType` respected

---

## 6. UI Requirements

- Queue tray per §29.28
- Honest offline copy per §29.14

---

## 7. API Requirements

_No new API surface in this epic._

---

## 8. Database Requirements

_No schema changes._

---

## 9. Security Requirements

- Persistence denial surfaced honestly
- No credentials in the outbox

---

## 10. Testing Requirements

- Kill-and-resume, airplane mode, backoff, cap, denial
